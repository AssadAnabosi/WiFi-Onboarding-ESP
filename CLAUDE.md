# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Arduino-framework boilerplate for Wi-Fi onboarding on ESP32: the device boots, tries saved STA credentials, falls back to a SoftAP (`192.168.4.1`, mDNS `config.local`), and serves a small web UI for scanning/connecting to networks and editing AP settings. Intended as a starting point for other IoT projects.

The `OTA` branch is implementing signed OTA updates per the spec doc https://claude.ai/artifact/SSL3ZAkp8mneuKfF5pAVp6 ("Implementation plan" lists the 20 steps; read it with the Claude Docs tools). The spec decides structure, naming and tooling going forward — e.g. LittleFS → NVS, web UI embedded in firmware — so check it before changing anything it covers.

## Build / flash workflow

There is no lint step. Python tests: `python -m unittest discover -s utils/tests` (needs `pip install -r utils/requirements.txt`).

CI (`.github/workflows/checks.yml`, every push/PR) runs those tests, reruns `build_assets.py` and fails on drift, validates target names (`python utils/targets.py check`), then compiles every `sketch.yaml` profile in its own job (`utils/targets.py prepare <target>` copies that target's `targets/<target>.partitions.csv` to `esp32/partitions.csv` and writes `build_opt.h` first; both are committed for the default target and `check` fails on drift) and checks the `.bin` against the target's app slot (`utils/targets.py size`, warns above 90%). Run the same commands locally before pushing.

- **Compile (CLI)**: `arduino-cli compile --profile esp32-4mb esp32` — the profile in `esp32/sketch.yaml` pins the ESP32 core (3.3.12; signing needs ≥ 3.3.8) and exact library versions, and arduino-cli installs them into its own internal cache. On this machine arduino-cli ships with the IDE at `%LOCALAPPDATA%/Programs/Arduino IDE/resources/app/lib/backend/resources/arduino-cli.exe`. Add `--build-path <dir>` to keep build output out of the repo.
- **Arduino IDE** ignores `sketch.yaml`: install the same core/library versions by hand and pick the "No FS 4MB (2MB APP x2)" partition scheme (matches `esp32/partitions.csv`).
- Both the IDE and arduino-cli automatically pick up `esp32/partitions.csv` and `esp32/build_opt.h` from the sketch folder. `build_opt.h` is a gcc response file, so string macros need escaped quotes (`-DFOO=\"bar\"`); its flags apply to the core and libraries too (e.g. `-DUPDATE_SIGN` enables `Update.installSignature`).
- **Web UI**: edit `web-interface/`, then run `python utils/build_assets.py` and commit the source change together with the regenerated `esp32/WebAssets.h` and `esp32/Version.h` (never edit those by hand; CI checks for drift). Output must stay byte-identical across machines: gzip uses the pinned `zopfli` (stdlib gzip differs between zlib and zlib-ng builds), JS uses `rjsmin` (css-html-js-minify breaks our JS), HTML/CSS use css-html-js-minify. `{{VERSION}}` in HTML is replaced from the root `VERSION` file, and local `css/`/`js/` links get `?v=<content hash>` (a page's ETag changes when anything it links changes); "(dev)" is appended at runtime by `js/api.js` from `/api/health`.
- **Previewing the UI** (no flashing): `python utils/ui_preview.py --mock` serves `web-interface/` on http://localhost:8766 with `js/api.js` and the page scripts swapped for the fake device `utils/ui_mock.js` (Demo states panel, state kept in `localStorage` `mock-state`); without `--mock` it serves the real scripts and forwards `/api/*` to `--device` (default `config.local`) with Host/Origin set to the device so the POST middleware accepts it. Standard library only. `ui_mock.js` must define every function the pages call (`test_ui_preview.py` checks); keep it in step when page behaviour changes.

- **Signing**: `utils/sign.py` turns `build/esp32.ino.bin` + `esp32.ino.partitions.bin` into `[firmware][128-byte info block][DER ECDSA P-256 signature zero-padded to 512]` (the core's `Update.installSignature` layout; info block = magic `WOTA`, format, firmware length, version, chip ID, SHA-256 of the 0xC00-padded partition table, target ID, project slug). `--verify FILE` checks one. `utils/keygen.py` makes keys (private keys go to gitignored `keys/`) and maintains the trusted release list in generated `esp32/OtaPublicKey.h` (`--add-public`, `--remove`, `--list`, `--check`); `keygen.py --dev` writes gitignored `esp32/OtaPublicKey.local.h`, whose presence makes a build a dev build (trusts dev + release keys, shows "(dev)"); `keygen.py --dev-manifest-url URL` adds `OTA_DEV_MANIFEST_URL` to it so dev builds check a local manifest (plain HTTP allowed, e.g. `python -m http.server`; `""` goes back to GitHub). `src/ota/OtaKeys.h` merges both lists; `TrustedKeyVerifier` (`src/ota/OtaVerifier.h`) tries each key.

- **Pulled updates** (`UpdateManager`, manifest parsing in `UpdateCheck`, HTTP in `HttpGet`): checks `https://github.com/<owner>/<repo>/releases/latest/download/manifest.json` 30 s after boot, then every 24 h + up to 1 h random, and on request, in a background task (HTTPS with the core's built-in certificate bundle, redirects followed, no NTP, 60 KB free heap required, STA connection required). Manifest: `{schema: 1, project, version, notes, targets: {<target>: {url, size, sha256}}}`, unknown fields ignored, a newer schema means "needs a manual install". Only a newer version for the running target is offered. The download streams through the same checks as a manual upload, plus size and SHA-256 against the manifest; release builds fetch HTTPS only.
- **Releases** (`.github/workflows/release.yml`, on a `v*` tag): a `validate` job (tests, drift, target names, `utils/release.py validate` = tag matches `VERSION`, newer than every existing GitHub release, `CHANGELOG.md` has a `## [X.Y.Z]` section; `release.py check-repo` = `OTA_GITHUB_OWNER/REPO` name this repo), one build job per target with no secrets and no cache (`targets.py prepare --commit <sha7>`), then a single `release` job in the protected `release` Environment: writes `OTA_SIGNING_KEY` to a temp file, `keygen.py --check`s it, signs and verifies each target, copies the core's `esp32.ino.merged.bin` as `.factory.bin`, `release.py manifest` writes `manifest.json` (notes = the changelog section) and `SHA256SUMS`, and publishes a **pre-release** (assets `<slug>-<version>-<target>.ota.bin`/`.factory.bin`, `manifest.json`, `SHA256SUMS`, `THIRD_PARTY_LICENSES.md`). Making it public is a manual step.
- **Browser installer** (`.github/workflows/pages.yml`, on a release made public or by hand): downloads every public release's `.factory.bin` files into `firmware/<version>/` (checked against `SHA256SUMS`) with the release body as `NOTES.md`; `release.py install` trims the images' 0xFF tail (safe: the page always installs from scratch, so ESP Web Tools erases the chip first), writes `<version>/install-<target>.json` per image and `install-index.json` (versions newest first with notes; targets in `sketch.yaml` order, title/description from each target header's `TARGET_TITLE`/`TARGET_DESCRIPTION`, which `targets.py check` requires; default profile = recommended; targets no longer in `sketch.yaml` listed by ID), adds ESP Web Tools from `npm pack` (pinned `ESP_WEB_TOOLS_VERSION`) and the page (`installer/` with its `favicon.ico`, `{{REPO}}` replaced, plus `web-interface/` `css/style.css`, `js/app.js` and `js/markdown.js`, so it shares the device's look, header and theme switch; `installer.css` hides the pill and maps ESP Web Tools' dialog variables (`--md-sys-color-*`, set on `ewt-install-dialog`/`ewt-no-port-picked-dialog`) to the UI tokens, `installer.js` repoints the brand), and deploys to GitHub Pages. Firmware is served from Pages because release downloads aren't CORS-readable. The page forces a new install (`checkSameFirmware` → false) since the factory image wipes settings. "Your own file…" accepts any full flash image (partition table at 0x8000, chip from the bootloader header) as blob: URLs, with an unsigned-file warning.
- **Updates & rollback**: `UpdateManager` is the one lock/state machine for every update path; `FirmwareSlots` owns the slot records and the confirmation window. `verifyRollbackLater()` (in `FirmwareSlots.cpp`) returns true so new firmware boots *pending*; it confirms itself (`esp_ota_mark_app_valid_cancel_rollback`) once `setup()` has finished (`firmwareSlots.setupDone()`) and it has run 60 s more; an `esp_timer` rolls it back at 3 min from boot, and the loop watchdog is on while unconfirmed. While unconfirmed, reboot, settings save, factory reset and new updates answer 409 "Finishing update, please wait N s". Slot records, home target, last-switch reason and the pending install live in the NVS `sys` namespace (`ConfigStorage`); on boot the running firmware's SHA-256 is compared with them to detect a USB flash or a rollback. Tested on hardware: rollback on reset and at the deadline both work.

## Architecture

The sketch lives in `esp32/` (`esp32.ino`); its code is in `esp32/src/`, one folder per module (`storage/`, `wifi/`, `web/`, `ota/`, `system/`), full table in `docs/architecture.md#code-layout`. The sketch root keeps only fork/tool-facing files (`ProjectConfig.h`, `build_opt.h`, `partitions.csv`, `sketch.yaml`, `targets/`, generated headers, `.clang-format`), so script/CI paths never point into `src/`; `src/` files include them by relative path (`"../../ProjectConfig.h"`). `esp32.ino` is the composition root: it creates `FirmwareSlots`, `UpdateManager(slots)`, `WiFiManager`, `WebServerManager(wifi, updates, slots)` and passes dependencies as constructor references (no `extern` globals); `setup()` starts `FirmwareSlots` first (rollback deadline armed before Wi-Fi), `setupDone()` last; `loop()` runs `firmwareSlots.loop()`, `updateManager.loop()`, `Restart::loop()`. Uses **ESPAsyncWebServer** with `AsyncCallbackJsonWebHandler` for JSON POST bodies (`AsyncJson.h` must be included after `ESPAsyncWebServer.h`; `.clang-format` has `SortIncludes: Never` for this).

Conventions: constants are `constexpr` in an anonymous namespace of the `.cpp` (only `ProjectConfig.h`, generated headers and build flags use `#define`); log with `LOG("<tag>", fmt, ...)` from `src/system/Log.h` (tags `cfg`, `wifi`, `web`, `ota`, `sys`); restarts go through `Restart::schedule(ms)`; format hand-written C++ with `esp32/.clang-format` (clang-format 14 ships with the Arduino IDE next to arduino-cli), never the generated headers. Only `web/` knows about HTTP requests and responses.

Modules:

- `storage/ConfigStorage` — static methods over NVS via `Preferences`: namespace `cfg` (user settings: `wifi_ssid`, `wifi_password`, `ap_ssid`, `ap_password`, `ap_channel`, `ap_hidden`, `ap_status`, `hostname`; cleared by factory reset together with `esp_wifi_restore()`) and `sys` (system records, kept). The Settings-page settings travel as one `DeviceSettings` struct (`loadSettings()`/`saveSettings()`; `ap_status` is `apEnabled`). All setting names live in one list at the top of `ConfigStorage.cpp`; every read takes a default (from `ProjectConfig.h`), so new settings need no migration. Setting-name rule (CONTRIBUTING.md): never rename, reuse or change a name's type; max 15 chars; retired names stay listed as reserved. Never log passwords. Adding a setting means: a key in that list, a `DeviceSettings` field read/written in `loadSettings()`/`saveSettings()` (and `logSettings()`), the GET/POST `/api/settings` handlers in `web/SystemRoutes.cpp`, a field in `settings.html`, `SETTING_KEYS` in `js/settings.js`, and `SETTINGS` in `utils/ui_mock.js`.
- `wifi/WiFiManager` — `begin()` (3 attempts with the saved network, then SoftAP if `ap_status` is true **or** STA failed, then mDNS `config.local`), `startConnect()` (background task; the blocking ~10 s `connect()` saves credentials on success; `attempt()` returns state + SSID under a mutex; on failure `restoreConnection()` reconnects to the saved network, else starts the SoftAP, before the state turns `failed`), `scan()` (background scan, results older than 15 s rescanned, sorted strongest first; returns a `ScanState`), `isScanning()`, `forgetNetwork()`. WPA2-Enterprise is encoded in the password field as `username|password` (configured via the core 3.x `esp_eap_client` API) — the stored config format is unchanged.
- `wifi/ImprovSerial` — Improv Wi-Fi serial (RPCs: Wi-Fi settings, current state, device info, scan) in its own task, started in `setup()` before `WiFiManager::begin()`; credentials wait for `WiFiManager::isReady()` and go through `startConnect()` (saved only on success); the redirect URL is `http://<STA IP>`. Each packet is one `Serial.write` ending in `
`, so it shares the port with `LOG`.
- `web/WebServerManager` — one class, routes split by area into `SystemRoutes.cpp` (`GET /api/health`, `GET /api/status`, `GET|POST /api/settings`, `POST /api/reboot`, `POST /api/reset`), `WifiRoutes.cpp` (`GET /api/scan`, 202 while a background scan runs; `POST /api/connect`, 202 with the result polled via `/api/status` → `station.attempt`; `POST /api/disconnect`) and `UpdateRoutes.cpp` (`POST /api/update`, raw `application/octet-stream` body, `?allow_downgrade=1` / `?allow_target_change=1` after the browser warned; `GET /api/update/status`, which also carries the last check: `check.state`, version, notes, `check.dev` = found in the local dev manifest; `POST /api/update/check` and `POST /api/update/install`, both 202 then poll the status; `POST /api/update/rollback` boots the other slot via `Update.rollBack()`, recorded as pending `manual_rollback`, offered only when `rollback_available` in `/api/status` is true: confirmed firmware whose last switch was `update` and whose other slot record is valid). `WebServerManager.cpp` serves the embedded UI from `WebAssets.h` (gzip, `ETag` = content hash, its own `304` handling; pages link CSS/JS as `file?v=<hash>` (added by `build_assets.py`), served `immutable` for a year when `v` matches, everything else `no-cache`) and has the response helpers: `{success, message}` via `sendMessage`/`sendJson` (any 2xx = success); `sendFailure` adds `error` for upload failures. `/api/status` also reports `project`, `chip_id` and `layout` (partition-table SHA-256) so the browser can apply the info-block rules before sending a file. Restarts are scheduled (`Restart`) and run from `loop()` after the response. A global middleware (`web/RequestGuard`) protects every POST (content type JSON/octet-stream, Host must be the device's own name, Origin must be its own pages); the upload route also runs it before writing to flash, since middleware only runs after the body. Note `server.on("/a")` also matches `/a/...`, so register longer routes first.
- `ota/UpdateManager` — upload/download/install state machine behind one mutex (`*Locked` methods expect it held); requests return `UpdateReply {status, error, message}`. Helpers: `ota/UpdateFile` (file layout constants, info-block parsing and rules, version compare), `ota/UpdateCheck` (manifest fetch and parse, check states), `ota/HttpGet` (redirect-following HTTP(S) GET, `isAllowedUrl`, `canFetch`), `ota/FirmwareSlots` (boot check, slot records, confirmation window and deadline, rollback availability; `Switch::*` are the stored last-switch strings), `ota/OtaVerifier` + `OtaKeys.h`.
- `system/` — `BuildInfo.h`, `Log.h`, `Restart`, and `CoreSerial` (optional debug helper that prefixes Serial lines with the core ID: `#define Serial SerialCore` in `esp32.ino`; it has no printf, so it doesn't combine with `LOG`).

Frontend (`web-interface/`): plain HTML/CSS/vanilla JS, no build step or framework, light and dark themes. One stylesheet, `css/style.css` (colour tokens on `:root`, overridden by `[data-theme="dark"]`). Each page is `<body data-page="…" data-version="{{VERSION}}">` with only its own content; `js/app.js` (in `<head>`, not deferred) sets the theme before first paint (saved choice in `localStorage`, else the system setting, else light) and builds the shared parts on `DOMContentLoaded`: header (brand, connection pill via `setStatus()`, theme toggle, tabs), the "Finishing update" bar, footer, the one `<dialog>` used by `ask()`, the toast host (`toast()`), and an eye button in every password field. It also has `showNote()` (sliding notes), `setFinishing()` (disables every `.lock-while-finishing`) and `firmwareBadge()`/`showUpdateNote()` ("Update available", "Dev update available" from `check.dev`, "Dev build", "Up to date"). Element ids must stay unique across a page and that chrome. `js/api.js` (deferred) has `api()` (XHR wrapper resolving to `{status, body}` or `null`; any device answer keeps the pill "Connected" and toasts the message, only no answer or a `502`/`504` (preview proxy) shows "Disconnected"), waits for `/api/health` (kept in `deviceInfo`: board info for the Home Device card) then calls the page's `load()`, checks `/api/update/status` on every page (calls the page's `onUpdateStatus()` if defined, runs the countdown while unconfirmed), and has `reloadAfterReboot()` and `mismatchText()`. Page scripts: `home.js`, `networks.js` (the Networks page: list with the connected network first, connect/disconnect, enterprise `username|password`, hidden networks), `settings.js`, and `firmware.js` (the Settings Firmware card: reads the picked file's info block, spots factory images, shows the spec's block/warning messages, uploads with a progress bar; release notes go through `renderMarkdown()` from `js/markdown.js`, loaded only on Settings and kept by the mock, which builds DOM nodes and never uses `innerHTML`). Use `esc()` when injecting API strings into `innerHTML`. Icons are inline SVG strings in `app.js` (Lucide, ISC).

## Other notes

- Defaults (AP SSID/password/channel, hostname, mDNS setup name), the GitHub owner/repo, `PROJECT_SLUG` and the update-check timing live in `esp32/ProjectConfig.h`; the build target (`OTA_TARGET_ID`, `OTA_TARGET_HEADER` → `esp32/targets/<target>.h`) comes from `build_opt.h`. Single source for the version: root `VERSION`.
- Untracked `main/`, `managed_components/`, `build/`, `sdkconfig*`, `dependencies.lock` in the working tree are ESP-IDF build leftovers, not part of the Arduino sketches on this branch.

## Working conventions

- Commit messages follow the Conventional Commits spec: https://www.conventionalcommits.org/en/v1.0.0/#specification (`type(scope): description`, optional body/footers, `!` or `BREAKING CHANGE:` for breaking changes).
- Do not add AI co-author trailers (e.g. `Co-Authored-By: Claude ...`) or any other AI attribution to commit messages.
- Whenever a phase or item of a plan/spec is finished, mark it as completed in that plan/spec file.
- Do not assume. If something is debatable, requires a choice the docs/specs don't specify, or conflicts with the docs, stop and ask the user — present the options along with your recommendation — before proceeding.
- Context management: when nearing the end of the context window, write a handoff for the next session based on the current step in the spec file (what's done, what's in progress, what's next). Never auto-compact unless the current step is fully done.
