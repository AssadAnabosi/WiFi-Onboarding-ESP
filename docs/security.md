# Security

Every update must carry a valid signature from a key the running firmware trusts. Since the update endpoints have no password, this signature is the main protection.

## Signed updates

The firmware uses the ESP32 Arduino core's built-in signed updates (`Update.installSignature`, enabled by `-DUPDATE_SIGN` in `esp32/build_opt.h`): ECDSA P-256 over SHA-256. The core is pinned to 3.3.12; **3.3.8 is the minimum**, because earlier versions fail to verify these signatures.

An update file (`.ota.bin`) is:

```text
[firmware][info block, 128 bytes][signature, 512 bytes]
```

The signature covers the firmware and the info block. It is DER-encoded and zero-padded to 512 bytes, the layout of the core's `tools/bin_signing.py`.

The info block says what the file is for:

| Field | Size | Purpose |
| --- | --- | --- |
| Magic `WOTA` | 4 B | Identifies an update file of this format |
| Format version | 2 B | Lets the layout change later |
| Firmware length | 4 B | Where the firmware ends |
| Version (major, minor, patch) | 6 B | Downgrade and newer-version checks |
| Chip type | 2 B | Blocks files for another chip |
| Layout hash | 32 B | SHA-256 of the partition table; blocks another flash layout |
| Target ID | 32 B | e.g. `esp32-4mb`; configuration checks |
| Project slug | 32 B | e.g. `wifi-onboarding`; blocks another project's file even when it is signed by a trusted key |
| Reserved | 14 B | Zero |

Numbers are little-endian; text is zero-padded. The device reads the info block as the file streams in and applies the version, chip, layout, target and project rules before the core checks the signature. A forged info block fails the signature check, and nothing is installed until both pass.

Pulled updates are fetched over HTTPS, using the core's built-in root certificate bundle, and must also match the size and SHA-256 in the release manifest. The signature is what makes them trustworthy, not the connection.

## Trusted keys

The firmware holds a short list of trusted public keys, generated by `utils/keygen.py`:

| Build | Trusts |
| --- | --- |
| Release (CI) | The release keys in `esp32/OtaPublicKey.h` |
| Dev (a local build that finds `esp32/OtaPublicKey.local.h`) | The dev key and the release keys |

- **Private release key:** never committed (`*.pem` and `keys/` are gitignored). It lives only in the `OTA_SIGNING_KEY` secret of the GitHub Environment `release`, which needs approval to run, plus an offline backup. CI writes it to a temporary file to sign and deletes it afterwards.
- **Public keys:** committed in `esp32/OtaPublicKey.h`, each with a short ID (`python utils/keygen.py --list`).
- **Dev key:** `python utils/keygen.py --dev`, local only (see [local-development.md](local-development.md#dev-keys)).

**Key rotation:**

1. Generate the new key (`keygen.py --out keys/ota-release-new.pem`). The header then trusts the old and new keys.
2. Release a version signed with the **old** key. Devices that install it trust both keys.
3. Change `OTA_SIGNING_KEY` to the new key, remove the old one (`keygen.py --remove <old ID>`), and release again.

**A leaked key** is retired the same way, as fast as possible. Devices that never received the release trusting the new key can only be recovered by USB flash. Until devices are updated, whoever holds the leaked key can sign updates for them.

## Cross-site request protection

Without protection, any web page open in a browser on the same network could send a hidden form to the device and trigger a factory reset, an install, a rollback, or an upload of an older signed release. Every POST route is therefore checked:

- **Content type** must be `application/json` or `application/octet-stream`. Browsers must ask before sending these to another site, and the device never answers that request (it sends no CORS headers). Plain HTML forms can't use these types.
- **Host** must be one of the device's own names: its access point IP, its network IP, `config.local`, its hostname or `<hostname>.local`. This blocks DNS-rebinding tricks.
- **Origin**, when the browser sends one, must be the device's own pages (`http://` plus one of those names).

A failed check answers `403` with the reason. Tools such as `curl` send no `Origin` and pass, which is expected: see the risks below. Release notes from the manifest are shown as plain text (never HTML), capped at 4 KB.

## Response headers

Every response carries `X-Content-Type-Options: nosniff`, so browsers use the declared type (`image/x-icon`, `application/json`, ...) and never guess one from the bytes. A file that isn't a script or a page, such as `favicon.ico`, can't be run as one.

## Generated and binary files

`esp32/WebAssets.h` is the web interface as gzipped bytes, which no reviewer can read. CI rebuilds it from `web-interface/` and fails if one byte differs (see [releasing.md](releasing.md#the-pipeline)), so its content can only change through the readable sources. Two things keep that check meaningful:

- The `main` ruleset requires the check to pass before merging (see [releasing.md](releasing.md#github-setup)).
- A pull request runs its own copy of the workflows and of `utils/build_assets.py`, so review changes to `.github/workflows/` and `utils/` as carefully as the firmware.

`web-interface/favicon.ico` is the one binary source file. It is embedded as is and served as `image/x-icon` with `nosniff`, so it can only ever be shown as an icon.

## Secure Boot

This project verifies OTA images in software. For production devices, use ESP32 **Secure Boot V2** plus **flash encryption**. This requires an ESP-IDF or PlatformIO build (Arduino as a component) and permanently configures the chip. The code doesn't need to change; the build system does.

## Known risks

- **Settings are stored unencrypted in flash**, Wi-Fi passwords included. Anyone with USB access to the device can read them.
- **The update endpoints have no password.** Anyone on the same network can use a tool such as `curl` to start an update, roll back, or downgrade to an older **signed** version, which may bring back fixed bugs.
- **The default access point password (`12345678`) is public.** Change it after setup. Forcing a change is planned (see [roadmap.md](roadmap.md)).
- **Forks that keep the upstream key** only accept upstream firmware and can't sign their own releases (see [make-it-yours.md](make-it-yours.md)).
- **No Secure Boot:** someone with physical access can flash any firmware over USB.
